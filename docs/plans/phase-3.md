# Phase 3 — Production-ready

This document plans Phase 3 from the [roadmap in AGENTS.md](../../AGENTS.md#4-roadmap).
Phase 1 built a RAG pipeline that works. Phase 2 made its retrieval better and
measurable. Phase 3 makes the service safe to expose to more than one caller.

Today every endpoint is open: anyone who can reach the port can upload, read,
delete, and query everything. Uploading a 200-page PDF blocks one HTTP request
for as long as the embedding provider takes. The same question asked twice costs
twice. And when an answer is wrong or expensive, there is no record of what the
service actually sent to the model. Phase 3 closes those four gaps, in that
order, because each one depends on the one before it: jobs and caches both need
to know *whose* data they are handling.

## Decisions

1. **One tenant per calling application; an API key identifies a tenant.**
   Authentication and multi-tenancy are not two features here, they are two
   halves of one: a key is only useful if it says *what* it grants access to,
   and a tenant is only enforceable if requests carry proof of who they are.
   An installation that serves a single app just creates one tenant and never
   thinks about it again; an installation serving several keeps their documents
   invisible to each other with no extra work.
2. **API keys are stored as an unsalted SHA-256 hash, not bcrypt or argon2, and
   not in plain text.** A key is 32 random bytes generated by the server, so it
   has ~256 bits of entropy. The slow, salted password hashes exist to make
   *guessing* expensive, and guessing only pays off against low-entropy secrets
   that humans chose. Against a random 256-bit secret, brute force and rainbow
   tables are equally hopeless, so bcrypt would buy nothing while costing
   ~100 ms of CPU **on every single request** - it would become the slowest
   thing in a cache hit. Unsalted also matters practically: a per-key salt makes
   the hash unlookupable, forcing a scan of every row to authenticate one
   request. With one hash function and no salt, authentication is a single
   indexed lookup on a unique column. Rejected: storing keys in plain text
   (a leaked database dump would be a leaked set of live credentials) and
   encrypting them (reversible, so the decryption key becomes the new secret to
   protect, and the service never needs to read a key back - only compare one).
3. **Tenant isolation is enforced by a `tenant_id` column that is filtered in
   application code, and `chunks` carries its own copy of it.** The column is
   denormalised onto `chunks` even though `chunks` already joins to `documents`.
   The reason is specific to vector indexes: pgvector's HNSW index is an
   *approximate* nearest-neighbour structure, and when a query filters on a
   column the index does not cover, PostgreSQL finds the `ef_search` nearest
   chunks **across all tenants** and only then throws the other tenants' rows
   away. Ask for 20 candidates in a database where another tenant owns most of
   the content, and you can get back three. A filter the index scan itself can
   see does not have this failure mode. Rejected: PostgreSQL Row-Level Security.
   RLS is genuinely stronger - the database refuses to return the rows at all,
   so a forgotten `WHERE` clause is not a data leak - but it needs a per-request
   `SET LOCAL app.tenant_id` on a pooled connection, it interacts awkwardly with
   Alembic and with the test suite's `TRUNCATE`, and it hides the filter from
   the code that reads like it is doing the filtering. The chosen mitigation for
   the weaker option is a test, not a comment: an isolation test that walks every
   endpoint as tenant B and proves tenant A's data is invisible. RLS stays a
   documented post-v1 hardening step.
4. **The first API key is created by a command-line tool, not an HTTP endpoint.**
   `uv run ragbridge-admin create-tenant --name acme` prints the key once and
   never again (only its hash is stored). An endpoint that mints credentials
   would itself need authentication - and the bootstrap problem would come
   straight back - or it would be an unauthenticated, internet-facing endpoint
   that hands out access. A command needs shell access to the server, which is
   a much higher bar and one the operator already has.
5. **Background jobs use `arq`, not Celery or RQ.** Phase 1 decision 1 made this
   codebase async all the way down, and `arq` is async-native: the worker can
   `await` the exact same `AsyncSession`, `Embedder`, and `chunk_text` the web
   process uses. Celery and RQ are both fork-and-block designs built around
   synchronous callables; either one would mean a second, synchronous database
   engine and a second copy of the ingestion path, maintained in parallel with
   the first. `arq` is also small enough to read in an afternoon, which matters
   for a project whose whole premise is "ready to use, not a framework".
6. **Asynchronous processing is chosen by size, and the API has one response
   shape either way.** `POST /documents` gains a `status` field
   (`pending` | `processing` | `ready` | `failed`). A small upload is processed
   in the request and comes back `ready`, exactly as it does today; an upload
   over `ASYNC_PROCESSING_THRESHOLD` is stored, enqueued, and comes back
   `pending`, with the client polling `GET /documents/{id}` until it is `ready`.
   Rejected: making every upload asynchronous (it changes the contract for
   existing callers and both evaluation scripts, and forces a polling loop on
   someone uploading a 2 KB FAQ) and returning a different shape - `202` plus a
   job id - for the async path (one endpoint, two response schemas, and every
   client needs both code paths anyway).
7. **The cache stores embeddings always, and whole answers only on request.**
   An embedding is a pure function of `(model, text)`: putting the model name in
   the cache key makes a stale hit impossible, so this one is free to switch on
   by default. A cached *answer* can go stale the moment a document is uploaded
   or deleted, so it is off by default and, when on, keyed by a per-tenant
   corpus version that any write bumps. Bumping a counter invalidates a tenant's
   entire answer cache without enumerating or deleting a single key: the old keys
   simply become unreachable and expire on their own TTL. Rejected: tracking which
   cached answers used which chunks so they can be invalidated precisely - correct,
   and far more bookkeeping than a counter, for a cache whose entries are cheap
   to recompute.
8. **Langfuse is off unless it is configured, and it is wired in through
   LiteLLM's callback rather than by wrapping every call site.** LiteLLM already
   knows the token counts and per-model prices for every provider it supports,
   so cost tracking is a callback registration rather than a pricing table this
   project would have to keep current. Retrieval is not an LLM call and does not
   appear on its own, so the query endpoint opens one explicit span around the
   whole operation for the LiteLLM spans to nest inside. With no keys set,
   nothing is registered and the code path is absent, not merely disabled - the
   key-free `docker compose up` story from Phase 1 keeps working untouched.

## Data model changes

- New `tenants`: `id` (UUID), `name`, `created_at`.
- New `api_keys`: `id` (UUID), `tenant_id` (FK, `ON DELETE CASCADE`),
  `key_hash` (unique), `prefix` (the first few characters of the key, for
  identifying it in a list or a log without revealing it), `name`,
  `created_at`, `last_used_at` (nullable), `revoked_at` (nullable).
- `documents` gains `tenant_id` (FK, `ON DELETE CASCADE`), `status`, and
  `error` (nullable - the failure reason when `status` is `failed`).
  `sha256` stops being globally unique and becomes unique **per tenant**:
  two tenants uploading the same file must get two independent documents,
  or the second one silently receives a document it does not own.
- `chunks` gains `tenant_id` (FK, `ON DELETE CASCADE`), denormalised from its
  document (decision 3), with the HNSW and GIN indexes rebuilt to include it.

## API changes

- **Every endpoint except `GET /health` requires `Authorization: Bearer <key>`**
  and returns `401` without a valid one. This is a breaking change for any
  Phase 2 client, and for both evaluation scripts, which gain an `--api-key`
  option.
- `GET /documents` lists only the calling tenant's documents;
  `DELETE /documents/{id}` returns `404`, not `403`, for a document belonging to
  another tenant - a `403` would confirm that the id exists.
- `POST /documents` responses gain `status` (and `error`, when failed).
- `POST /query` searches only the calling tenant's chunks.

## New settings

| Setting | Default | Meaning |
|---|---|---|
| `REDIS_URL` | `redis://localhost:6379/0` | Queue and cache connection |
| `ASYNC_PROCESSING_THRESHOLD` | `100_000` | Uploads larger than this many bytes are processed by the worker |
| `EMBEDDING_CACHE_TTL` | `86400` | Seconds a cached embedding lives (`0` disables) |
| `ANSWER_CACHE_ENABLED` | `false` | Whether whole answers are cached (decision 7) |
| `ANSWER_CACHE_TTL` | `3600` | Seconds a cached answer lives |
| `LANGFUSE_PUBLIC_KEY` | `""` | Enables tracing when set together with the secret key |
| `LANGFUSE_SECRET_KEY` | `""` | |
| `LANGFUSE_HOST` | `https://cloud.langfuse.com` | Self-hosted Langfuse instances point this elsewhere |

## Steps

1. Tenants, API keys, and the `Authorization: Bearer` dependency; the
   `ragbridge-admin` command
2. Multi-tenant scoping of documents, retrieval, and the evaluation scripts
3. Redis and the `arq` worker; document `status` and asynchronous processing of
   large uploads
4. Embedding cache and optional answer cache
5. Langfuse tracing and cost tracking; README, docs, ADRs, ready for `v0.2.0`

Each step is built as several small, focused commits on its own feature branch.

## Step 1 detail — tenants, API keys, and authentication

Branch: `feat/phase-3-auth` (created from `main`, off the merged Phase 2).
This step creates the tables, the way in, and the way to mint a key. It does
**not** scope any data yet: after this step a valid key is required to reach an
endpoint, but every key still sees everything, because `documents` and `chunks`
do not know about tenants until step 2. Splitting it this way keeps two hard
things - "is this request authenticated" and "which rows may it see" - in
separate, separately testable commits. Proposed commit breakdown:

1. **`docs: add Phase 3 plan`** (this document).
2. **`feat(db): add tenants and api_keys tables`**
   - `Tenant` and `ApiKey` ORM models as described under "Data model changes",
     plus one Alembic migration creating both.
   - `api_keys.key_hash` gets a **unique** index: it is what authentication
     looks a request up by, so it must be both fast and impossible to
     duplicate.
   - No application code uses these tables yet.
   - Tests: create a tenant with a key and read both back; deleting a tenant
     cascades to its keys (the `ON DELETE CASCADE` is what stops revoked
     tenants leaving live credentials behind).
3. **`feat(auth): add API key generation and verification`**
   - New `src/ragbridge/auth.py`, holding the parts that are pure functions and
     therefore testable without a database: `generate_api_key() -> str` returns
     `"rb_" + secrets.token_urlsafe(32)` (`secrets`, not `random` - `random` is
     a deterministic pseudo-random generator seeded from the clock, fine for
     simulations and disqualifying for credentials), and
     `hash_api_key(key: str) -> str` returns its SHA-256 hex digest
     (decision 2).
   - `api_key_prefix(key)` returns the first 11 characters (`rb_` plus eight),
     which is what gets stored for display. Eight random characters is enough
     to tell two of a tenant's keys apart and far too little to guess the rest.
   - Tests: two generated keys differ; a key round-trips through
     `hash_api_key` to the same digest every time; the digest does not contain
     the key.
4. **`feat(auth): require an API key on every endpoint except /health`**
   - `get_tenant` dependency in `auth.py`: reads the credentials with FastAPI's
     `HTTPBearer` security scheme, hashes them, and looks up the `ApiKey` row
     by `key_hash` with `revoked_at IS NULL`, returning the joined `Tenant`.
     Anything missing, unknown, or revoked raises `401` with the same message -
     an error that distinguished "no such key" from "revoked key" would be a
     free oracle for anyone probing.
     `HTTPBearer` rather than a plain `X-API-Key` header for two reasons: it
     puts an **Authorize** button in the generated `/docs` UI, and it is the
     shape a PHP caller already knows from Laravel Sanctum or Symfony's
     `access_token` authenticator.
   - The dependency is added to the `documents` and `query` routers as a
     router-level dependency, not to each endpoint by hand: a new endpoint on
     those routers is then authenticated by default, and forgetting to add it is
     not possible. `health` stays public, so container health checks and load
     balancers keep working without a credential.
   - `last_used_at` is refreshed only when it is missing or more than an hour
     old. Writing it on every request would turn every authenticated `GET` into
     a write transaction, for a field nobody reads at minute resolution.
   - Tests: no header → `401`; a malformed header → `401`; an unknown key →
     `401`; a revoked key → `401`; a valid key → the endpoint's normal
     response; `GET /health` works with no header at all.
   - `tests/conftest.py` grows a `tenant_with_key` fixture and an
     authenticated-client fixture, and `_reset_database` starts truncating
     `api_keys` and `tenants` as well. Every existing test moves to the
     authenticated client - the diff is large and shallow, and it is exactly the
     change every Phase 2 client will have to make too.
5. **`feat(cli): add the ragbridge-admin command`**
   - New `src/ragbridge/admin.py` with `create-tenant`, `list-tenants`,
     `create-key`, and `revoke-key`, registered as a `ragbridge-admin`
     entry point in `pyproject.toml` (decision 4). Argument parsing uses the
     standard library's `argparse`; a CLI with four subcommands does not need a
     dependency.
   - `create-tenant` and `create-key` print the generated key **once**, with a
     line saying it cannot be shown again, because only its hash is stored.
   - `revoke-key` sets `revoked_at` rather than deleting the row, so an audit
     of what a leaked key touched is still possible afterwards.
   - Tests: `create-tenant` writes a tenant and a key, and the printed key
     authenticates a request; `revoke-key` makes that same key stop working.
     The second test is the one that proves revocation is real rather than
     cosmetic.

## Step 2 detail — multi-tenant scoping of documents, retrieval, and evaluation

Branch: `feat/phase-3-tenancy` (created from `main`, off the merged step 1).
Step 1 authenticates a request and resolves it to a tenant, but nothing yet
reads that tenant: every key still sees every document and every chunk. This
step closes that gap.

**Refined while implementing decision 3:** the plan as written said a filter
the index scan itself can see - denormalising `tenant_id` onto `chunks` -
avoids the HNSW under-return problem. That is necessary but, on its own, not
quite sufficient: the database actually installed is pgvector **0.8.6**
(verified against the running container, not assumed), which supports
**iterative index scans** (added in pgvector 0.8.0) - a scan mode built for
exactly this failure. Without it, a `WHERE tenant_id = ...` filter next to an
`ORDER BY embedding <=> ...` still lets PostgreSQL's planner walk the HNSW
graph for its ordinary quota of neighbours *before* checking the filter, on a
column HNSW has no index-native way to prune by ahead of time. `SET LOCAL
hnsw.iterative_scan = 'relaxed_order'` makes the scan keep walking until it
has actually found `limit` matching rows (bounded by `hnsw.max_scan_tuples`,
default 20000), instead of stopping early and only then discarding the rows
that fail the filter. `vector_search` sets this per-query, inside the same
session/transaction as the query it precedes, so it never leaks into other
queries on the same connection. `relaxed_order` (not `strict_order`) accepts
slightly out-of-distance-order matches in exchange for not restarting the
walk from scratch at every step - an acceptable trade here, since
`reciprocal_rank_fusion` and the reranker both re-sort this candidate set
anyway. `keyword_search`'s GIN index is an exact match, not an approximation,
so it needs the tenant filter and nothing more.

Proposed commit breakdown:

1. **`docs: add Phase 3 step 2 plan`** (this section).
2. **`feat(db): add tenant_id to documents and chunks`**, **`feat(retrieval):
   scope vector and keyword search by tenant`**, and **`feat(api): scope
   documents and query by tenant`** - **corrected while implementing: these
   three land as one commit, not three.** Once `tenant_id` is `NOT NULL`,
   `POST /documents` violates that constraint on its very next write until it
   is updated to set it - there is no order of separate commits across these
   three that leaves every intermediate commit's test suite green, unlike step
   1, where each table or function was inert until the next commit wired it
   in. Splitting them here would only produce commits that fail in isolation,
   which is worse than one honestly-sized commit. What follows describes the
   combined commit's content, organised by concern:
   - `tenant_id` (FK to `tenants.id`, `ON DELETE CASCADE`, indexed) added to
     both tables; migration `3cb3c5c7dcce`. Both tables were empty in every
     environment this ran against, so the column is added `NOT NULL` directly,
     no backfill step.
   - `documents.sha256`'s unique constraint moves from `sha256` alone to
     `(tenant_id, sha256)` - two tenants uploading the same file must get two
     independent documents (decision 3's "sha256 unique per tenant" is only
     meaningful once this constraint matches it).
   - Tests: the existing `Document`/`Chunk` round-trip tests in
     `test_models.py` now create a `Tenant` first and pass its id.
   - `vector_search` and `keyword_search` both gain a required `tenant_id`
     keyword argument and filter on it; `hybrid_search` threads it through to
     both arms. `vector_search` additionally sets `hnsw.iterative_scan` (see
     above).
   - Tests: `test_retrieval.py`'s direct calls to both functions now resolve a
     `tenant_id` from the test's API key (via a small helper - these tests
     call the functions directly, not through the API, so they need an actual
     id, not a header) and pass it through.
   - `POST /documents`, `GET /documents`, `DELETE /documents/{id}`, and
     `POST /query` each take `Annotated[Tenant, Depends(get_tenant)]`
     directly, replacing step 1's router-level `dependencies=[Depends(get_tenant)]`
     (every endpoint now actually uses the resolved tenant to scope a query,
     so declaring it once per endpoint - not once per router as a
     side-effect-only check - is both authentication and the value the
     endpoint needs, in one dependency).
   - `POST /documents`: new documents and chunks are stamped with
     `tenant.id`; the duplicate-upload check filters by tenant too.
   - `GET /documents`: filters by `tenant.id`.
   - `DELETE /documents/{id}`: looks the document up **by id and tenant
     together**; a document belonging to another tenant is indistinguishable
     from a missing one and returns `404`, never `403` (API changes,
     above) - a `403` would confirm the id exists, which is itself
     information a caller should not get for data it cannot see.
   - `POST /query`: `hybrid_search` is called with the caller's `tenant.id`.
3. **`test(auth): add a tenant isolation test`**
   - The mitigation decision 3 calls for in place of Row-Level Security: one
     test file that creates two tenants, uploads a distinct document to each,
     and walks every endpoint as tenant B asserting tenant A's data is
     invisible - `GET /documents` never lists it, `DELETE` on tenant A's
     document id returns `404` under tenant B's key, and `POST /query` with a
     question that only matches tenant A's content returns no sources under
     tenant B's key. This is the safety net for choosing application-level
     filtering over RLS: a forgotten `WHERE` clause fails this test loudly,
     the same day it is introduced, rather than leaking silently.
